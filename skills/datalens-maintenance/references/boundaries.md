# Maintenance boundaries

- `dl_backup_export` writes exact readbacks plus `manifest.json`. `artifact_kind=snapshot_not_full_restore` and `restore_verified=false` are deliberate until a disposable end-to-end restore is demonstrated.
- `dl_cleanup_preview` reads exact candidates, preserve roots and their direct relations. It closes preservation within candidates; an external consumer blocks deletion, including a preserve path through a non-candidate. It does not recursively scan unrelated root branches. Apply only an unchanged preview whose ordered delete set is repeated exactly; a missing target is `already_absent`, not a batch-wide failure.
- For standalone HTML Page lifecycle and its distinct iframe contract, use [HTML Pages](html-pages.md). Read active capabilities before claiming a phase is supported.
- Admin inventory is read-only. License assignment is a separate mutation. No revoke capability is claimed.
- Use [authorized scope and delivery](../../datalens-dashboard/references/authorized-scope.md) for authorization, uncertain effects and multi-object completion.

Cleanup identity is the provider entry ID regardless of inventory aliases. Preview retains original preserve roots, reads both relation directions and orders consumers before dependencies. Incomplete or external-consumer scope is a boundary; API-visible relations are not proof of tenant-wide completeness. Apply revalidates the original scope; reconcile `preview_changed` with the authorized set and preserve requirements. Failed or uncertain deletion stops remaining objects and requires reconciliation, not retry or recreation.

Cleanup has one operation budget (`budget_sec`, default 120, maximum 180) and a provider-call limit (`max_provider_calls`, default 200). Retain its phase, completed/remaining reads and typed failure; an incomplete preview never permits apply. Do not automatically repeat the entire scan or increase the host timeout. The preview supplies an `operation_id` before apply; retain it or supply an explicit ID. `dl_operation_get` remains available during the domain call. After a lost response or restart, use `dl_operation_reconcile` for exact readback without another delete. A fresh `preview_changed` means this preflight dispatched no new delete, not that an older unknown delete failed. A still-readable object after an admitted delete remains uncertain; cancellation stops new dispatches and does not undo an in-flight effect.

If the user separately authorizes another possible delete after being told the earlier outcome is unknown, `dl_cleanup_apply` accepts `repeat_of: [{operation_id, object_id, receipt_version}]`. Read the original receipts and use their current `store_version` as `receipt_version`; reference every unknown cleanup for each repeated target. Use a fresh complete preview, its exact `confirmed_delete` and a new operation ID. This argument asserts the existing informed authorization; it is not proof of a new human reply. Ordinary cleanup permission alone does not authorize it. Pending operations, changed receipt/auth scope, unlisted unknown effects and changed dependencies remain barriers. An admitted repeat retains the originals and records its references. A possible effect consumes that grant; another unknown result requires new informed authorization covering the latest receipt too. A proven `not_applied` failure permits a corrected in-scope attempt without another permission question. Reusing the same operation ID only reads/reconciles; it never dispatches again.
