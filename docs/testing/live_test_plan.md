# Повторяемая live-приёмка R1–R3

Эта карточка используется при relevant release/приёмке, не при каждом пользовательском задании. Запускайте только явно разрешённый сценарий на собственных диагностических объектах. Полные ответы, точные ID/GUID, конфигурация и Browser evidence хранятся в частном локальном каталоге вне plugin source и Git.

## Зафиксировать до запуска

Сохраните неизменный текст обычного задания, source Dataset/workbook, точные GUID и смысл меры/даты/категории, формулу/агрегацию, timezone и границы периода, source revision и доступную идентичность данных, authoring config, модель/effort/host и исходное состояние. Release плагина — изменяемая переменная. Запишите role→ID собственных объектов. Не используйте уже удалённые ID. При дрейфе данных отметьте новый baseline; исторические суммы и расход не являются идентичным сравнением. Не меняйте expected после результата ради PASS.

Модель получает обычное задание построить индикатор продаж за январь 2026 со сравнением с декабрём 2025 и фильтром категории на зафиксированном Dataset в оформлении проекта. Использует установленный authoring skill. Сохраните первый compiled candidate до исправлений. Общий period binding читает живой Dataset; статические prepared_data и ручная подмена Sources недопустимы.

## R1 — адресное чтение и два периода

1. Из точного project/subproject root проверьте native `dl_server_info`, `dl_auth_check` и адресно source Dataset. Не начинайте полный inventory для известного target. Подтвердите SUM меры и прежние GUID, даты 2026-01-01…2026-01-31 и 2025-12-01…2025-12-31, согласованную семантику границ.
2. Используйте один собственный KPI и один Dashboard с selector group. Переиспользование требует доказанного ownership и исходного состояния; не копируйте Dataset/connection. Сохраните первый candidate и выполните настоящий save/readback → publish-from-saved → published readback.
3. Получите четыре адресных контрольных агрегата последовательно: All за каждый период, одна фиксированная категория за каждый период. Не создавайте параллельную нагрузку. Контроль All переиспользуется для Reset; trend не заменяет source total.
4. В опубликованном UI пройдите **All → все три категории → выбранная категория → Reset**. Сверьте оба значения с контрольными агрегатами. Проверьте widget title/hint, выключенный Dashboard title, отсутствие внутреннего title/description, реальные labels, отсутствие ненужной сетки и устойчивые цвета. Сохраните доступное Browser evidence; не заявляйте неподдержанный export.

## R2 — тот же граф и cleanup

На том же Dashboard сопоставьте native snapshot и `dl_object_relations(direction="from")` по прямым зависимостям; `direction="to"` KPI должен показать потребителя. Ограниченная страница честно возвращает continuation, только если он есть. Полнота не означает транзакционность.

В `dl_cleanup_preview` задайте Dashboard как preserve root и подтвердите защиту KPI. Не вызывайте защищённый apply ради отказа. В конце получите свежий complete preview только собственных объектов и передайте exact `confirmed_delete` в `dl_cleanup_apply`: Dashboard, затем KPI. Подтвердите отсутствие адресными reads, сохранность исходного Dataset и чужих объектов. При частичном графе или неизвестном эффекте не повторяйте удаление; укажите остаток и квитанцию.

## R3 — естественный 429

Наблюдайте обычную последовательность R1/R2 без повышения concurrency или fault injection. При естественном 429 сохраните безопасные метаданные, неизменный payload, фактические интервалы, `rate_limited`, известный Retry-After и ограниченное последующее чтение без раннего повтора. Следуйте [правилу rate-limit recovery](../../skills/datalens-inspect/references/direct-reads.md#rate-limits).

Если 429 не возник: **«новая ветка 429 не наблюдалась live»**. Исторический лог обосновывает дефект, но не выполнение нового кода. Не провоцируйте потерю записи или повреждённую страницу, не подменяйте HTTP/SDK ради PASS. Этот честный предел не блокирует поставку.

Достаточен предыдущий сопоставимый baseline и один relevant проход после установки. Повторяйте только затронутую часть после новых изменений/ошибки. Отчёт разделяет offline checks, installed runtime, native MCP, API/data, Browser и cleanup.
